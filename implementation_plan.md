# Implementation Plan: “Fun Recaps” on Dashboard (3 Versions, Hall of Fame, Album Takeover, Plot Twists)

This document is written so an engineer/agent can implement the feature set **without prior context** beyond this repository.

Goal: add four “Wrapped-like” recap sections to the existing dashboard page (`app/(protected)/dashboard/page.tsx`) using **only** the Supabase snapshot data already collected daily, and compute analytics via **Postgres RPCs** defined in `supabase/migrations/*.sql`.

## 0) Repository Context (What This App Is)

- Framework: Next.js App Router (Next 16).
- Auth + DB: Supabase.
- Data collection: a Supabase Edge Function that runs daily and stores “top 50” ranked snapshots for each user/time-range.
  - Edge function: `supabase/functions/collect-snapshots/index.ts`
  - It creates one `snapshots` row per `(user_id, time_range, day)` and inserts related rows into ranking tables (artist/track/album).
- Dashboard entry point (protected): `app/(protected)/dashboard/page.tsx`
  - Currently fetches “live top lists” from Spotify and merges `previous_rank` based on latest snapshot (`lib/spotify/helpers.ts`).
  - The new recaps should **not** rely on live Spotify calls; they should use **stored snapshot/ranking** data so they still work offline.

## 1) Core Terms / Glossary

- **Time ranges** (`snapshots.time_range`):
  - `short_term`: last ~4 weeks
  - `medium_term`: last ~6 months
  - `long_term`: all time
- **Snapshot**: a daily capture of the user’s top 50 lists for a single time range.
- **Chart appearance**: an item (artist/album/track) exists in the top 50 for a snapshot (i.e., there is a row for it in a ranking table for that snapshot).
- **Rank delta**: `previous_rank - rank` for a ranking row (positive = climbed, negative = dropped).
- **Dropout**: the item appears in snapshot T but not in snapshot T+1 (absence inferred; no explicit row is stored for “not in chart”).
- **Takeover** (albums): `album_rankings.track_count` indicates how many of the day’s top tracks belong to that album; takeover percent = `track_count / 50`.

## 2) Constraints & Product Rules

- **Do not call “ranked lists” play counts.**
  - You do not have Spotify play counts. You have “Top 50” ranks per snapshot day.
  - UI copy must say things like:
    - “Most days in your Top 50” (not “most replayed”)
    - “Most #1 days”
    - “Peak rank”
    - “Takeover: 18/50 tracks”
- **Respect `user_profiles.stats_visibility`**: `public`, `followers`, `private`.
  - Even though this work starts on a protected dashboard, enforcing visibility in RPCs keeps them safe for future “public recap pages” or friend views.
- **Heavy computation belongs in Postgres.**
  - Add RPCs (functions) via `supabase/migrations/*.sql`.
  - The app will call `supabase.rpc(...)` from server components.
- **Don’t edit autogenerated files**:
  - Do not edit `supabase/schema/schema.sql`.
  - Do not edit `lib/supabase/database.ts` by hand. Regenerate after migrations.

## 4) UX Scope Decisions (Entity Coverage)

To maximize “identity” and minimize noise:
- **3 Versions of You**: artists + albums (skip tracks).
- **Album Takeover**: albums only.
- **Hall of Fame**: artists + albums (skip tracks for MVP).
- **Plot Twists**: artists + albums (skip tracks for MVP).

Tracks can be revisited later (V2) once the recaps feel good.

## 5) Analytics Strategy (Why Dropouts/History Work)

You will still have data for items that “fall out” of the latest snapshot because historical ranking rows remain in the database. The only missing part is explicit “absence” markers.

To detect dropouts you compare consecutive snapshots for a time range:
- Build ordered snapshots with `LEAD(snapshot_id)` (next snapshot).
- Join ranking rows for snapshot T to snapshot T+1 on item_id:
  - “Dropped out” = present in T, missing in T+1.

This is easy and efficient in SQL when scoped to a time window (e.g., last 30–365 days).

## 6) Security / Visibility Enforcement (Required for All RPCs)

### Why RPC-level enforcement

Supabase functions in this codebase frequently use `SECURITY DEFINER`. That bypasses Row Level Security, so **every recap RPC must**:
- check viewer authorization via `auth.uid()`
- check target profile’s `stats_visibility`
- only return data for `p_target_user_id` if permitted

### Visibility rules

Let:
- viewer = `auth.uid()` (nullable)
- target = `p_target_user_id`
- target setting = `user_profiles.stats_visibility`

Rules:
- If viewer == target: allow.
- Else if setting == `public`: allow.
- Else if setting == `followers`: allow only if viewer is authenticated AND `check_friendship_status(viewer, target)` is true.
- Else (`private`): deny.

### Return style

Prefer a helper function `assert_can_view_user_stats` that throws (so the app gets a clear error).
For UX, the dashboard (owner view) should not hit the denial path; but the RPCs must still implement it.

### 7.1) `20260111_01_recaps_visibility.sql`

Add:
- `public.can_view_user_stats(p_target_user_id uuid) returns boolean`
- `public.assert_can_view_user_stats(p_target_user_id uuid) returns void`

Skeleton:
```sql
create or replace function public.can_view_user_stats(p_target_user_id uuid)
returns boolean
language plpgsql
stable
security definer
set search_path to 'public', 'pg_temp'
as $$
declare
  viewer_id uuid := auth.uid();
  visibility text;
begin
  if p_target_user_id is null then
    return false;
  end if;

  if viewer_id = p_target_user_id then
    return true;
  end if;

  select up.stats_visibility
  into visibility
  from public.user_profiles up
  where up.user_id = p_target_user_id;

  if visibility is null then
    return false;
  end if;

  if visibility = 'public' then
    return true;
  end if;

  if visibility = 'followers' then
    if viewer_id is null then
      return false;
    end if;
    return public.check_friendship_status(viewer_id, p_target_user_id);
  end if;

  return false; -- private
end;
$$;

create or replace function public.assert_can_view_user_stats(p_target_user_id uuid)
returns void
language plpgsql
stable
security definer
set search_path to 'public', 'pg_temp'
as $$
begin
  if not public.can_view_user_stats(p_target_user_id) then
    raise exception 'stats_visibility_denied' using errcode = '42501';
  end if;
end;
$$;

grant execute on function public.can_view_user_stats(uuid) to anon, authenticated;
grant execute on function public.assert_can_view_user_stats(uuid) to anon, authenticated;
```

### 7.2) `20260111_02_three_versions.sql` (3 Versions of You)

RPC:
- `public.get_three_versions_of_you(p_target_user_id uuid, p_limit int default 10) returns jsonb`

Return contract (must include these keys/fields):
- `artists.short_term|medium_term|long_term`: arrays of `{ id, name, image_url, rank }`
- `artists.constants`: ids present in all 3
- `artists.unique_short|unique_medium|unique_long`: present only in that time range among the 3 lists
- `artists.biggest_shift_long_vs_short`: array of `{ id, name, image_url, short_rank, long_rank, delta }`
- same structure under `albums.*`

SQL approach (concrete query plan):
- Resolve latest snapshot per time_range (3 snapshot IDs).
- Fetch top `p_limit` artists + albums for each snapshot ID.
- Compute:
  - constants: `short ∩ medium ∩ long`
  - unique_short: `short - (medium ∪ long)` (and similarly for other ranges)
  - biggest_shift_long_vs_short: join `short` and `long` on `id`, compute `delta = long_rank - short_rank` (or the inverse; pick one and keep it consistent in UI copy)

Suggested CTE building blocks (drop into the function and adapt names as needed):
```sql
with latest_snapshots as (
  select time_range, id as snapshot_id
  from (
    select
      s.time_range,
      s.id,
      row_number() over (partition by s.time_range order by s.created_at desc) as rn
    from public.snapshots s
    where s.user_id = p_target_user_id
  ) ranked
  where ranked.rn = 1
),
artist_short as (
  select
    ar.artist_id as id,
    ar.artist_name as name,
    ar.artist_image_url as image_url,
    ar.rank
  from public.artist_rankings ar
  join latest_snapshots ls on ls.snapshot_id = ar.snapshot_id
  where ls.time_range = 'short_term'
  order by ar.rank asc
  limit p_limit
),
artist_medium as ( ...same for medium_term... ),
artist_long as ( ...same for long_term... ),
artist_constants as (
  select id from artist_short
  intersect
  select id from artist_medium
  intersect
  select id from artist_long
),
artist_unique_short as (
  select id from artist_short
  except
  (select id from artist_medium union select id from artist_long)
),
artist_shift_long_vs_short as (
  select
    s.id,
    s.name,
    s.image_url,
    s.rank as short_rank,
    l.rank as long_rank,
    (l.rank - s.rank) as delta
  from artist_short s
  join artist_long l on l.id = s.id
  order by abs(l.rank - s.rank) desc, l.rank asc
  limit least(p_limit, 10)
)
select ...
```

Implementation note:
- Don’t return raw CTE tables; aggregate them into predictable arrays using `jsonb_agg(...)` with stable ordering.

### 7.3) `20260111_03_album_takeover.sql` (Album Takeover)

RPC:
- `public.get_album_takeover_recap(p_target_user_id uuid, p_days int default 90) returns jsonb`

Return contract:
- For each time range key (`short_term`, `medium_term`, `long_term`):
  - `latest`: `{ date, album_id, album_name, album_image_url, track_count, takeover_percent } | null`
  - `record`: same fields, max `track_count` within window
  - `most_frequent`: `{ album_id, album_name, album_image_url, days_at_1 } | null`
  - `timeline`: array of `{ date, album_id, album_name, album_image_url, track_count, takeover_percent }` ordered ascending by date (limit e.g. last 30–90 rows as needed)

SQL approach:
- For each time range:
  - filter snapshots by `created_at >= now() - (p_days || ' days')::interval`
  - join `album_rankings` on `snapshot_id` where `rank = 1`

Suggested CTE building blocks:
```sql
with window_snapshots as (
  select s.id, s.time_range, date(s.created_at at time zone 'utc') as day, s.created_at
  from public.snapshots s
  where s.user_id = p_target_user_id
    and s.created_at >= now() - (p_days || ' days')::interval
),
top_album_per_snapshot as (
  select
    ws.time_range,
    ws.day,
    ar.album_id,
    ar.album_name,
    ar.album_image_url,
    ar.track_count,
    (ar.track_count / 50.0) as takeover_percent
  from window_snapshots ws
  join public.album_rankings ar on ar.snapshot_id = ws.id
  where ar.rank = 1
),
latest_per_range as (
  select distinct on (time_range) *
  from top_album_per_snapshot
  order by time_range, day desc
),
record_per_range as (
  select distinct on (time_range) *
  from top_album_per_snapshot
  order by time_range, track_count desc, day desc
),
most_frequent_per_range as (
  select
    time_range,
    album_id,
    max(album_name) as album_name,
    max(album_image_url) as album_image_url,
    count(*) as days_at_1
  from top_album_per_snapshot
  group by time_range, album_id
)
select ...
```

Implementation notes:
- `album_rankings.rank` is derived at snapshot time from `track_count` sorting, so `rank = 1` is the “takeover winner” for that snapshot.
- Timeline length: consider limiting to `least(p_days, 90)` rows per time range to keep payload sizes small.

### 7.4) `20260111_04_hall_of_fame.sql` (Hall of Fame)

RPC:
- `public.get_hall_of_fame_recap(p_target_user_id uuid, p_days int default 365, p_limit int default 10) returns jsonb`

Return contract:
- For each time range:
  - `artists.most_days_charted`: array of `{ id, name, image_url, days_charted }`
  - `artists.most_number_one_days`: `{ id, name, image_url, number_one_days }`
  - `artists.best_peak_rank`: `{ id, name, image_url, peak_rank }`
  - `artists.longest_streak`: `{ id, name, image_url, longest_streak_days }`
  - same for `albums.*` (use album fields, not artist)

Longest streak computation (snapshot-per-day assumption):
- Use snapshot day = `date(s.created_at at time zone 'utc')`.
- For each item’s ordered days, compute streak groups using:
  - `day - row_number() * interval '1 day'` trick (classic gaps-and-islands).

Suggested streak CTE:
```sql
with item_days as (
  select
    ar.artist_id as id,
    max(ar.artist_name) as name,
    max(ar.artist_image_url) as image_url,
    date(s.created_at at time zone 'utc') as day
  from public.snapshots s
  join public.artist_rankings ar on ar.snapshot_id = s.id
  where s.user_id = p_target_user_id
    and s.time_range = 'medium_term'
    and s.created_at >= now() - (p_days || ' days')::interval
  group by ar.artist_id, date(s.created_at at time zone 'utc')
),
streak_groups as (
  select
    id,
    day,
    (day::timestamp - (row_number() over (partition by id order by day) * interval '1 day')) as grp
  from item_days
),
streak_lengths as (
  select id, grp, count(*)::int as streak_len
  from streak_groups
  group by id, grp
),
max_streak as (
  select id, max(streak_len)::int as longest_streak_days
  from streak_lengths
  group by id
)
select ...
```

Implementation note:
- Reuse the same pattern for albums (`album_id`, `album_name`, `album_image_url`).

### 7.5) `20260111_05_plot_twists.sql` (Plot Twists)

RPC:
- `public.get_plot_twists_recap(p_target_user_id uuid, p_days int default 30, p_limit int default 20) returns jsonb`

Return contract:
- For each time range:
  - `artists`: array of “events”
  - `albums`: array of “events”

Event shape (consistent across artists/albums):
- `{ event_type, date, item_id, item_name, item_image_url, rank, previous_rank, delta, context }`
  - `event_type` in: `biggest_climb`, `biggest_drop`, `new_entry_top10`, `dropped_out_after_top10`
  - `delta` nullable (e.g. for dropouts where next rank doesn’t exist)
  - `context` is optional jsonb for extra fields (e.g. `{"next_date":"...", "was_rank": 7}`)

How to compute each event type:
- biggest climb/drop:
  - ranking rows with `previous_rank is not null`
  - `delta = previous_rank - rank`
  - take top/bottom by delta, but cap to avoid spam:
    - optionally return “best of each day” then pick top `p_limit`
- new_entry_top10:
  - `previous_rank is null and rank <= 10`
- dropped_out_after_top10:
  - build snapshot pairs `(snapshot_id, next_snapshot_id)`
  - pick items in top 10 on snapshot_id
  - left join to next snapshot’s ranking rows for the same item_id; missing => dropout event

Suggested CTE for snapshot pairs:
```sql
with ordered_snapshots as (
  select
    s.id as snapshot_id,
    date(s.created_at at time zone 'utc') as day,
    lead(s.id) over (order by s.created_at asc) as next_snapshot_id
  from public.snapshots s
  where s.user_id = p_target_user_id
    and s.time_range = 'medium_term'
    and s.created_at >= now() - (p_days || ' days')::interval
),
current_top10 as (
  select
    os.day,
    os.snapshot_id,
    os.next_snapshot_id,
    ar.artist_id as id,
    ar.artist_name as name,
    ar.artist_image_url as image_url,
    ar.rank,
    ar.previous_rank,
    (ar.previous_rank - ar.rank) as delta
  from ordered_snapshots os
  join public.artist_rankings ar on ar.snapshot_id = os.snapshot_id
  where ar.rank <= 10
),
dropouts as (
  select
    ct.day as date,
    ct.id,
    ct.name,
    ct.image_url,
    ct.rank,
    ct.previous_rank
  from current_top10 ct
  left join public.artist_rankings next_ar
    on next_ar.snapshot_id = ct.next_snapshot_id
   and next_ar.artist_id = ct.id
  where ct.next_snapshot_id is not null
    and next_ar.id is null -- dropped out
)
select ...
```

Implementation notes:
- “biggest climb/drop” is usually more meaningful when restricted to items currently in the top 10–20 (otherwise you get noise from rank 49→30). Decide a cutoff and document it (recommended: `rank <= 20`).
- Keep the payload intentionally small (default `p_limit` 20) and stable ordering (e.g., by `abs(delta)` desc, then rank asc).

## 8) Performance & Indexing

Existing indexes cover artists/tracks history well. Albums have fewer.

Add these indexes (either in `20260111_04_hall_of_fame.sql` or a dedicated migration):
```sql
create index if not exists idx_album_rankings_user_album
on public.album_rankings using btree (user_id, album_id);

create index if not exists idx_album_rankings_history
on public.album_rankings using btree (user_id, album_id, created_at desc);
```

Also consider (optional) for faster “latest snapshot per time range”:
```sql
create index if not exists idx_snapshots_user_time_range_created
on public.snapshots using btree (user_id, time_range, created_at desc);
```
